# Engineering Playbook

本手册说明如何执行根目录 `AGENTS.md`。它描述通用工程流程，不保存当前项目进度，也不替代用户的具体需求。

## 1. 为什么采用这套方式

本仓库早期五轮开发反复证明：稳定交付依赖可复现案例、最小变更、真实验证、人工检查点和可回滚路径，而不是越来越长的聊天记录或状态文档。

这套流程也对应成熟工程实践：

- [AGENTS.md](https://github.com/agentsmd/agents.md) 为编码代理提供仓库级常驻指令；
- [GitHub Spec Kit](https://github.github.com/spec-kit/index.html) 使用“规格 → 计划 → 任务 → 实现”的规格驱动流程；
- [Google Engineering Practices](https://google.github.io/eng-practices/) 强调小而完整的变更、同行审查和测试随代码同行；
- [GitHub分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges/managing-protected-branches/about-protected-branches) 通过必需检查约束合并；
- [MADR](https://adr.github.io/madr/) 和 [Google Cloud ADR指南](https://docs.cloud.google.com/architecture/architecture-decision-records) 用轻量记录保存重要决定的背景与后果。

本项目只采用适合小型私人项目的最小组合，不引入完整企业流程。

## 2. 最小任务路由

本项目不采用企业级工单分类、复杂度分数或风险矩阵。Codex 只做足以选择流程的判断。

### 2.1 是否只读

如果用户只要求解释、调研、诊断、审查或状态报告，按 Read-only 处理，不修改文件或外部状态。

### 2.2 需要改动时选择一个类型

| 类型 | 判断标准 | 核心流程 |
|---|---|---|
| Bug | 已有行为与明确预期不一致 | 复现、根因、失败回归测试、最小修复、验证 |
| Feature | 增加或改变用户可观察能力 | 场景、范围、方案、验收案例、最小实现、验证 |
| Task | 重构、依赖、测试、文档、构建、数据或运行操作 | 明确目标，采用与实际风险相称的规则和验证 |

### 2.3 只判断两个附加条件

- **Long?** 是否命中 `AGENTS.md` 的长任务条件；
- **High-risk?** 是否涉及数据、索引、安全、权限、外部写入、部署、不可逆迁移或可能破坏当前可用版本。

Long 或 High-risk 任一为“是”，都必须创建 `CURRENT_WORK.md`。High-risk 还必须设置人工批准点和回滚路径。

不使用 Small/Standard/Long 等多档评分，不使用 Low/Normal/High/Emergency 风险等级，也不由 Codex 判断业务优先级。除非分类会触发建档、审批或停止，Codex 无需把内部分类过程输出给用户。

发现新证据后可以升级控制强度；一旦升级为 Long 或 High-risk，必须暂停实现并先创建 `CURRENT_WORK.md`。

## 3. 通用启动检查

每次开发或修复开始时：

1. 运行 `git rev-parse --show-toplevel` 确定当前实际 checkout，并读取该根目录的 `AGENTS.md`；
2. 用一句话复述要解决的问题；
3. 读取相关代码、测试、配置和最近 Git 变更；
4. 检查工作树，区分用户改动与当前任务；
5. 当前 checkout 根目录只要存在 `CURRENT_WORK.md`，就运行 `python scripts/check_current_work_hygiene.py --repo .`；不得按主观任务归属跳过，失败时不得进入实现；
6. 写出明确范围和非目标；
7. 确定什么证据能够证明完成；
8. 判断是否需要调研、设计审批、`CURRENT_WORK.md` 或 ADR；
9. 在没有失败案例、验收标准或批准方案时，不进入实现。

### 3.1 疑难问题升级与成熟经验调研

是否“不能快速解决”按证据判断，不设固定时长。出现以下任一信号时立即升级：

- 一次有界的聚焦诊断或最小实验结束后，仍不能说明根因、故障层或下一项能够证伪的验证；
- 同一解决路径连续失败两次，继续尝试只是在叠加补丁、扩大重试或更换未经证实的参数；
- 问题涉及团队或代理不熟悉的技术、版本兼容、平台差异、外部集成、协议、格式、算法或安全边界；
- 准备自写解析器、转换器、重试框架、调度器、兼容层或其他通常已有成熟实现的通用能力。

触发后按以下顺序执行：

1. **停止扩散**：保留复现输入、日志、失败测试和当前 Git 状态；停止继续堆叠猜测性修改，不扩大范围；
2. **定义检索问题**：写清实际失败、适用版本、平台、输入输出、安全限制和候选方案必须通过的固定案例；
3. **先查仓库**：检查已有代码、测试、配置、依赖、注释和相关 Git 历史，避免建立第二套实现；
4. **再查一手资料**：优先查看适用版本的官方文档、参考实现、迁移或变更记录、上游 issue 与已知限制；
5. **比较成熟实现**：必要时检查维护良好的开源工具和行业通行模式，比较功能匹配、版本兼容、维护状态、许可证、依赖规模、运行成本、安全影响和回退方式；
6. **做最小验证**：先运行上游最小示例或隔离原型，再用当前固定失败案例验证，不直接把候选方案接入主路径；
7. **作出决定**：优先采用现有方案，其次薄封装或组合；只有证据证明这些方案不适用、不足或成本不可接受时，才允许为当前案例编写最小自定义实现。

普通任务不为调研另建永久文档。长任务或高风险任务把关键来源、适用条件、验证结果、被否决原因和下一动作写入 `CURRENT_WORK.md`；其他任务在当前任务记录、测试和差异中保留足以审查的证据。若无法访问必要资料、无法核验许可证或无法运行最小示例，应报告实际阻塞并请求决定，不得把“没找到”写成“没有成熟方案”。成熟经验是候选证据，不替代本地复现、回归测试、专业判断、人工批准或安全门禁。

## 4. CURRENT_WORK.md

### 4.1 创建时机

创建条件以 `AGENTS.md` 为准。它是活动任务的临时控制面，不是新的项目基线。

### 4.2 固定模板

创建根目录 `CURRENT_WORK.md` 时使用以下结构。超过 12 KiB 时 checker 发出警告；超过 16 KiB 或 120 行时失败：

```markdown
# Current Work: <任务名称>

Status: active
Started: <YYYY-MM-DD>
Branch/Worktree: <分支和工作树>

## Objective
一句话说明要实现的结果。

## Active Scope
- 本次必须完成的内容。

## Non-goals
- 明确不做的内容。

## Authoritative State
- 当前 HEAD、分支、工作树、Git 状态、有效证据和关键失败。

## Approval and Rollback
- 已批准对象、范围、条件、停止点和回滚路径。

## Complexity Budget
- User-visible acceptance: 当前必须证明的结果。
- New dependencies: none，或列出已批准依赖。

## Temporary Artifacts
- None

## Unique Next Action
后续任务可以直接执行的唯一下一步。
```

没有临时产物时保留 `- None`。如有临时产物，删除 `- None`，每项使用：`path=<绝对路径> | owner=<任务> | purpose=<用途> | recovery=<恢复方式> | cleanup=<清理条件>`。

### 4.3 更新规则

- 只在里程碑、根因、范围、审批点或下一动作变化时更新；
- 新发现的坑一旦有足够证据影响后续路径，应立即更新，不等待会话结束；新证据推翻旧结论时同步修订或删除过期记录；
- 每条记录必须区分事实、推断和待确认内容；
- 不能把测试尚未通过写成已经完成；
- 跨会话前必须在 `Authoritative State` 中记录当前 Git 状态和失败点，并保持唯一下一动作；
- 当前任务完成后先提炼长期资产，再删除该文件。

### 4.4 冲突处理

若发现一个与当前请求无关的活动 `CURRENT_WORK.md`：

- 先运行仓库卫生 checker，不覆盖、不删除、不修改、不擅自继续；
- 检查是否进入错误分支或工作树；
- 停止或切换到正确 checkout；不得以“继承”“外来”或“不匹配当前任务”为由跳过门禁。

### 4.5 可接管状态

长任务不能只在预计换会话时才补写交接信息。每完成一个里程碑、获得批准、发现关键根因或失败、改变范围，或者开始可能跨越当前会话的工作前，都应刷新 `Authoritative State`、相关生命周期字段和 `Unique Next Action`，使意外中断最多丢失当前尚未完成的原子操作。

交接记录必须满足：

- 事实、推断和待确认内容能够区分；
- Git 状态能够说明哪些是本任务改动，哪些是用户已有改动；
- 验证记录包含实际命令、退出状态和结论，历史结果不冒充当前结果；
- 批准记录包含具体对象、范围和条件，不写“用户已同意全部继续”等宽泛表述；
- 坑记录包含可识别的触发条件、失败证据、禁止重复项、替代路径和失效条件，不只写“这里有坑”“之前失败过”等无法执行的提醒；
- `Unique Next Action` 只有一个，说明执行对象、前置条件和预期证据，不能写成多个候选步骤；
- 不写入密钥、凭据、私有全文或敏感客户资料。

### 4.6 有序中断与停驻交接

用户在长任务尚未完成时提出“做好跨会话交接并停止”或同义要求，无论当前仍在执行，还是当前回合或阶段已经停止并等待用户，都按以下顺序处理：

1. 不再启动新的业务工作、里程碑或范围；只允许为安全停止、状态核验和更新交接记录所必需的工具调用；
2. 若存在活动操作，判断它能否安全截断。短时且原子的操作可以完成；耗时且可取消的操作在不破坏文件、数据或仓库状态的位置取消；不能安全截断的写入、迁移切换或 Git 操作必须先完成当前原子步骤或回滚。若不存在活动操作，直接进入状态检查；
3. 检查是否遗留运行中的进程、半写文件、锁、临时状态或不明确的外部副作用，并如实记录；
4. 更新 `CURRENT_WORK.md` 的状态、当前范围、权威状态、批准、临时产物和唯一 `Unique Next Action`；
5. 重新读取交接相关段落，确认下一会话无需依赖当前聊天即可判断做什么；
6. 向用户报告已停在哪个安全点、哪些内容尚未完成以及下一动作，然后停止。不得执行该下一动作。

若工具调用尚未返回或尚未进入可取消状态，应在它返回或到达安全取消点后处理请求。因此执行中的有序中断表示“尽快安全停止”，不承诺瞬时终止；当前回合或阶段已经停止时，则立即进行状态核验和交接更新，不恢复业务执行。

### 4.7 新会话接管

新会话收到“继续当前长任务”或同义要求后：

1. 按通用启动检查读取 `AGENTS.md`、工程手册和 `CURRENT_WORK.md`；
2. 确认用户请求与活动任务的目标一致；
3. 核对工作树绝对路径、分支、HEAD 和 `git status --short`，解释与交接记录之间的每项变化；
4. 逐项读取 `Findings and Failures` 中仍有效的坑，确认下一动作没有重复已证实失败的路径。只有出现足以推翻原结论的新证据或适用条件已经变化时才能重新验证，并先记录旧结论为何不再适用；
5. 核对唯一下一动作依赖的文件、证据、工具和外部状态仍然存在；
6. 核对所需人工批准已明确记录，且批准对象、范围和条件没有变化；
7. 核验通过后直接执行唯一下一动作，不重新讨论已批准方案，不重复已有有效证据，也不再次索要已记录且仍有效的批准；
8. 核验失败时停止并报告具体不一致，由用户决定恢复状态、修订下一动作、切换工作树或重新批准。

接管只能恢复已记录范围。“继续当前长任务”不授权新范围，也不能绕过发布、部署、外部发送、生产写入、不可逆操作或权限变更原有的批准门禁。

## 5. 新功能开发流程

### 5.1 需求与场景

先回答：

- 谁使用；
- 当前遇到什么真实问题；
- 不做会怎样；
- 成功后用户能完成什么；
- 哪些内容明确不属于本次范围。

用户表述可能不专业时，应从目标和真实行为理解需求，但不能借“优化”扩大授权。

### 5.2 调研与方案

需要新依赖、框架、算法、外部服务或新架构时，必须执行疑难问题升级门禁中的成熟经验调研，并先检查：

1. 仓库已有能力；
2. 官方文档和成熟实现；
3. 维护状态、许可证、依赖规模和运行成本；
4. 采用、薄封装、组合或自建的取舍；
5. 当前固定失败案例是否真的需要它。

至少比较两个合理方案。推荐方案必须说明为什么适合当前规模。

### 5.3 设计审批

以下变更必须在编码前展示设计并获得批准：

- 新页面或明显改变用户流程；
- 新数据库、索引、模型或外部服务；
- 数据格式、权限或安全边界变化；
- 会产生持续费用或不可逆迁移；
- 用户明确要求先看方案、线框或计划。

### 5.4 Golden-first

实现前先建立验收证据：

- 可回答案例指定准确预期；
- 不可回答案例明确禁止的输出；
- 现有案例和目标不得为了新实现而漂移；
- 先记录当前基线，再修改实现；
- 不把不相关数据绑定为方便通过的目标。

### 5.5 实现与验证

按最小自洽阶段实现。每阶段都应保持系统可运行，并执行：

1. 新案例或失败测试；
2. 最小实现；
3. 专项测试；
4. 相关模块测试；
5. 全量测试；
6. 与用户真实路径一致的动态验证；
7. 差异和复杂度审计。

## 6. Bug 修复流程

### 6.1 复现

记录：

- 精确输入和环境；
- 预期结果；
- 实际结果；
- 是否稳定复现；
- 首次出现的版本或相关提交；
- 日志、截图、堆栈或状态证据。

无法复现时继续缩小变量，不直接提交猜测性修复。

### 6.2 根因

区分症状与根因。使用单变量实验、日志、最小复现或已有测试定位故障发生层。对间歇性问题先判断是否为资源释放、并发、环境、时序或外部依赖，再决定是否允许有界重试。

若一次有界诊断仍无法确定根因或下一项有效验证，或同一路径已连续失败两次，立即返回第 3.1 节执行成熟经验调研。不得继续叠加猜测性修复、无界重试或自写通用替代组件。

### 6.3 回归测试

回归测试必须：

- 在修复前因原问题失败；
- 失败信息能够指向被修复行为；
- 在修复后通过；
- 不依赖无关网络、时间或环境偶然性；
- 保留用户可观察行为，而不是锁定内部实现细节。

### 6.4 最小修复

只修改根因路径。若发现相邻重构需求，除非不处理就无法安全修复，否则记录为独立任务。

### 6.5 验证层次

1. 原始复现路径；
2. 新回归测试；
3. 相关测试；
4. 全量测试；
5. 真实环境路径；
6. 安全、性能、兼容性和回滚检查。

## 7. 验证矩阵

| 变更 | 最低验证 |
|---|---|
| 纯文档 | 文件存在、链接/术语、范围和 Git 差异 |
| 纯重构 | 现有相关测试与全量测试，证明行为不变 |
| 业务逻辑 | 新测试、相关测试、全量测试 |
| UI | 自动化测试、真实浏览器正负路径、关键交互 |
| 模型/RAG | 固定 golden、真实模型调用、证据门禁负例 |
| PDF/文件 | 解析、真实页面、路径和元数据验证 |
| 数据/索引 | 预检、暂存构建、完整性、切换、失败保持和回滚 |
| 外部集成 | 沙箱或受控目标、错误路径、权限和重复调用安全 |

测试命令以仓库当前配置为准。历史命令和结果必须先核对仍适用，不能机械复制。

## 8. 复杂度自省

在调研后、设计后、关键实现后和最终验收前分别检查：

- 新代码是否由当前验收案例直接需要；
- 是否存在更简单的成熟方案；
- 是否增加第二事实源、第二数据库或第二流程；
- 是否预建没有调用方的接口；
- 是否把一次性 Demo 做成生产平台；
- 是否能删除某层而仍满足全部验收；
- 是否为了表面成功降低证据或安全门槛。

无法用失败案例或明确要求说明必要性的复杂度不进入当前变更。

## 9. 清理与删除

清理不是低风险的收尾动作。删除任何文件或目录前，必须先确认目标的绝对路径、归属、现有内容、可重建性和恢复方式；目录名、文件扩展名、Git 忽略状态以及“缓存”“临时”“测试产物”等标签都不能单独证明可以整体删除。

### 9.1 删除前预检

1. 解析并核对目标的绝对路径，确认没有落到仓库根目录、用户目录、资料目录、正式索引或其他宽泛范围；
2. 用只读清单检查目标现有内容，区分本轮创建、历史遗留、共享缓存、用户文件和来源不明内容；
3. 确认目标由谁创建、是否为本轮独占、是否可由确定步骤安全重建；
4. 确认删除后的恢复方式。可行时优先移动到隔离目录、回收站或其他可恢复位置；
5. 若无法确认归属、范围、可重建性或恢复方式，停止清理并请求用户决定。

### 9.2 可执行范围

- 本轮独占创建、内容可重建且绝对路径已经核实的临时目录，可以整体删除；
- 共享缓存、历史测试目录或同时包含本轮与既有内容的混合目录，只能删除本轮明确创建的文件，不得为了清理本轮产物而删除既有内容；
- 包含来源不明内容、历史验证证据、用户文件、客户资料或其他无法确认内容的目录，不得继续清理，必须由用户决定；
- 化工资料、正式索引、客户数据、审阅记录及不可恢复产物，未经当前任务的明确授权不得删除；
- 不能把本规则解释为“所有目录永远不能整体删除”。是否允许整体删除，只取决于目标是否为本轮独占、范围是否明确、内容是否可安全重建并具有可接受的恢复路径。

### 9.3 删除后的报告与验证

删除完成后必须说明：

- 删除目标的绝对路径和实际范围；
- 删除的是本轮产物，还是其中包含既有内容；
- 删除内容能否恢复，以及恢复方式；
- 是否检查并确认未影响用户文件、受控资料、正式索引、客户数据或其他任务产物。

必要时重新列出父目录或运行相关验证，证明删除范围没有扩大。不得用“目录已被 Git 忽略”“工具生成的文件通常可重建”代替实际核验。

## 10. 决策记录与运行手册

### 10.1 ADR

只有决定会长期影响多个模块，并且难以撤销、不记录原因很可能导致错误回退时，才按需创建 ADR。ADR只保存背景、备选方案、决定、后果和回退条件，不保存任务进度；普通功能、Bug、局部重构和容易撤销的选择不创建 ADR。

### 10.2 Runbook

只有同时满足以下条件才创建运行手册：

- 操作以后会重复；
- 包含容易遗漏的顺序、检查点或回滚；
- 已至少真实成功执行一次；
- 自动化暂时不比人工步骤更可靠或更经济。

Runbook记录命令、输入、预检、停止点、成功标准和回滚，不建立第二套产品需求。

### 10.3 任务文档收口

任务文档按内容寿命处理，不按“已经写入 Git”或“任务已经完成”决定去留：

- 代码、测试、配置、必要 ADR、稳定规范和已验证运行手册属于可提交成果；
- `CURRENT_WORK.md`、任务状态、交接快照、临时计划、完成清单、过程日志、评审草稿和可重建验收产物属于临时控制面；
- 任务完成后，先把仍有长期价值的信息迁移到可提交成果，再在同一收口变更中删除临时控制面；
- 收口时逐项审查活动坑：只对当前任务、临时环境或已经失效的记录直接删除；只有适用条件稳定、未来任务很可能再次遇到且复发代价明显的内容，才迁移到最接近事实的代码、回归测试、稳定工程规则、必要 ADR 或已验证运行手册；
- 长期资产只保留可复用的触发条件、根因证据、防复发约束、正确路径和失效条件，不复制任务流水账。以后证据证明该坑失效时，必须更新或删除对应长期资产；
- 同一文档同时包含活动与已完成内容时，只保留当前未完成范围、仍有效门禁、阻塞和唯一下一动作；
- 提交和推送只用于保存可复用成果，不能作为保留流水账、重复规格或历史状态的理由；
- 不建立 `archive`、`history`、`completed` 等目录保存已完成任务文档。确需追溯时使用 Git 历史、Issue 或 PR。
- 不建立 `pitfalls`、`lessons-learned`、避坑汇总等目录或文档保存已完成任务的坑；不得为了保留坑而延迟删除 `CURRENT_WORK.md`。

## 11. 收口

完成前必须：

1. 在当前工作状态运行新鲜验证；
2. 检查失败数、退出码和真实输出；
3. 核对 Git 差异只包含授权范围；
4. 说明未运行的验证及原因；
5. 清理临时进程、任务状态、交接快照、临时计划、完成清单、过程日志和可重建验收产物；
6. 对长任务提炼长期资产；整个任务完成时删除 `CURRENT_WORK.md`，任务切换时将其精简到当前活动范围；
7. 未经授权不提交、不推送、不部署；
8. 最终答复只报告有证据支持的完成状态、重要限制和下一步。
